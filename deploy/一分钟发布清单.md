# Erwang Blog 一分钟发布清单

> 适用场景：
>
> - 修一个前端 bug 后快速上线
> - 修一个后端接口后快速上线
> - 前后端一起改完后快速上线

这份清单只保留**最常用、最短路径**，不讲大原理。需要看完整背景请看：

```text
deploy/服务器部署与运维手册.md
```

## 0. 发布前先判断：你改了哪一层？

### 只改了前端（Vue 页面 / 样式 / 交互）
走：**前端快速发布**

### 只改了后端（Java 接口 / 权限 / SQL 逻辑）
走：**后端快速发布**

### 前后端都改了
走：**全量快速发布**

### 改了数据库结构
不要直接照这份“快速清单”硬上，先看完整手册里的数据库章节。

## 4. 如果改了数据库结构

### 原则

不要再像首次部署那样直接删库重建，除非你明确知道线上数据不要了。

### 正确做法

1. 先备份数据库
2. 写增量 SQL
3. 在服务器执行 SQL
4. 再发后端 jar

### 备份命令

```bash
mysqldump -uroot -p blog > /root/blog_backup_$(date +%F_%H%M%S).sql
```

## 7. 出问题时的最短回滚思路

### 前端出问题

把上一次备份的前端静态文件重新覆盖回去。

### 后端出问题

如果发布前备份过 jar：

```bash
cp /www/server/erwang/backend/app.jar.bak_时间戳 /www/server/erwang/backend/app.jar
systemctl restart erwang
```

### 数据库出问题

用备份 SQL 恢复，不要现场硬改。

## 8. 我个人建议的固定习惯

每次发布前，先做这 4 件事：

1. `git status`
2. `git add . && git commit -m "..."`
3. 本地打包
4. 记住本次发的是前端、后端还是全量

这样以后线上出问题时，知道自己到底发了什么。

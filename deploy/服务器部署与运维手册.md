## 2. 当前线上架构总览

### 2.1 当前正式结构

前端、后端、数据库不是放在一起乱跑，而是分成三层：

```text
用户浏览器
   ↓
https://erwang.me
   ↓
Nginx（宝塔站点）
   ├── 直接返回前端静态文件
   └── /api 反向代理到 Spring Boot
                 ↓
         http://127.0.0.1:9090
                 ↓
             MySQL 5.7
         127.0.0.1:3306
```

### 2.2 这样设计的原因

- **前端静态文件**适合交给 Nginx，性能稳定
- **后端接口**不直接暴露公网，安全性更高
- **数据库**只给本机访问，避免 3306 暴露到公网
- **域名访问统一走 80/443**，用户不需要知道后端端口

## 4. 本次部署过程中实际做了什么

这一节按真实操作顺序说明。

### 4.1 先本地打包前端和后端

#### 前端打包

```bash
cd /Users/miaozesheng/study/erwang/frontend
npm run build
```

**作用：**

- 把 Vue 项目编译成生产可用的静态文件
- 生成 `dist/` 目录，供 Nginx 直接托管

#### 后端打包

```bash
cd /Users/miaozesheng/study/erwang/backend
mvn clean package -DskipTests
```

**作用：**

- 把 Spring Boot 项目打成可运行的 jar
- 最终产物是：

```bash
backend/target/blog-backend-1.0.0.jar
```

---

### 4.2 上传前后端产物到服务器

最终采用的是：

- 前端覆盖到：`/www/wwwroot/erwang`
- 后端放到：`/www/server/erwang/backend/app.jar`

这样做的原因：

- 宝塔已有站点根目录就是 `/www/wwwroot/erwang`
- 不需要推翻旧站点目录结构
- 后端单独放到 `/www/server/erwang`，避免和前端混在一起

---

### 4.3 重建数据库并导入完整表结构

这次部署中，数据库不是直接沿用旧库，而是**重建 blog 库后重新导入**。

原因：

- 服务器上旧库是旧版本结构
- 旧表结构和现在代码不一致
- 例如 `user` 表字段和新版本代码不一致，导入时出现过 `Unknown column 'role'` 报错

最终做法：

1. 删除旧 `blog` 数据库
2. 重建 `blog`
3. 重新导入 `backend/sql/init.sql`

### 4.4 为什么要补全 `init.sql`

这次部署前，我检查了项目实体类，发现原始 SQL 缺了三张表：

- `article_like`
- `article_favorite`
- `quick_link`

所以现在仓库里的 `backend/sql/init.sql` 已经被补完整，可以用来在**干净 MySQL 5.7** 上直接建表。

---

### 4.5 配置后端环境变量

后端最终不是把敏感配置写死在代码里，而是放到：

```bash
/www/server/erwang/deploy/erwang-backend.env
```

这样做的原因：

- 数据库密码不写死在仓库里
- JWT 密钥不进 Git
- 以后改域名、改上传目录、改数据库密码更方便

核心环境变量包括：

- `SPRING_PROFILES_ACTIVE=prod`
- `SERVER_PORT=9090`
- `DB_HOST=127.0.0.1`
- `DB_NAME=blog`
- `DB_USERNAME=bloguser`
- `DB_PASSWORD=...`
- `JWT_SECRET=...`
- `CORS_ORIGINS=https://erwang.me,https://www.erwang.me`
- `APP_UPLOAD_DIR=/www/server/erwang/uploads`

---

### 4.6 调整 Nginx 反向代理

当前实际生效的是宝塔站点配置 + 代理子配置。

关键点只有两个：

#### 站点根目录

```nginx
root /www/wwwroot/erwang;
```

#### API 反代

```nginx
location ^~ /api/ {
    proxy_pass http://127.0.0.1:9090/api/;
}
```

**作用：**

- 浏览器访问 `https://erwang.me/api/...`
- Nginx 转发到本机 Spring Boot `9090`

这样前端生产环境只需要：

```env
VITE_API_BASE=/api
```

不需要把服务器 IP 写死进前端代码。

---

### 4.7 把后端交给 systemd 托管

一开始我们先用 `nohup` 手动启动，是为了先排除项目本身问题。

确认接口正常后，再切到 `systemd`。

这样做的原因：

- 启动失败时更容易定位
- 真正上线后需要开机自启和守护
- `systemd` 比临时 `nohup` 更稳定

## 7. 当前还需要注意的一件事

这次部署过程中，HTTPS 曾出现“您的连接不是私密连接”。

最可能原因是：

- 当前证书原本给 `erwang.top` 申请
- 现在站点又同时服务 `erwang.me`
- 如果证书 SAN 不包含 `erwang.me` / `www.erwang.me`，浏览器会报证书不匹配

所以后续要检查：

- 宝塔 SSL 中绑定的证书是否覆盖 `erwang.me`
- 是否同时覆盖 `www.erwang.me`

## 8. 服务器重启后的恢复检查流程

这一节的目标是：**服务器重启后，不要慌，按固定顺序检查网站是否恢复正常。**

### 8.1 为什么重启后还要人工检查

虽然现在后端已经交给 `systemd` 托管，Nginx 和 MySQL 也通常会跟着系统启动，但重启之后仍然可能出现：

- MySQL 启动慢于后端，导致后端第一次启动失败
- Nginx 启动了，但证书 / 配置没有按预期加载
- 后端虽然进程在，但接口报错
- 前端静态文件没问题，但 `/api` 代理不通

所以建议每次重启后都走一遍下面的检查顺序。

### 8.2 第一检查：先看后端服务是否在运行

```bash
systemctl status erwang
```

你希望看到的是：

```text
Active: active (running)
```

如果不是 `active (running)`，继续看日志：

```bash
journalctl -u erwang -n 100 --no-pager
```

### 8.3 第二检查：看数据库是否还在

```bash
systemctl status mysqld
```

如果你的系统里服务名不是 `mysqld`，也可以用：

```bash
ps -ef | grep mysql | grep -v grep
```

### 8.4 第三检查：看 Nginx 是否正常

```bash
nginx -t
systemctl status nginx
```

### 8.5 第四检查：直接测后端接口

```bash
curl http://127.0.0.1:9090/api/articles
```

如果能返回 JSON，说明：

- Java 服务起来了
- 数据库连接基本正常
- 接口层在工作

### 8.6 第五检查：测域名是否正常

```bash
curl https://erwang.me/api/articles -k
curl -I https://erwang.me -k
```

如果 API 正常但网页打不开，优先检查：

- Nginx 反代是否被改坏
- 证书是否过期/不匹配
- 宝塔站点根目录是否被误改

### 8.7 如果重启后服务没起来，最快恢复方法

按顺序执行：

```bash
systemctl restart mysqld
systemctl restart erwang
nginx -t && nginx -s reload
```

然后再测：

```bash
curl http://127.0.0.1:9090/api/articles
```

## 9. 后续本地 Git 代码有修改时，怎么快速发布

这一节解决的是最常见的问题：

> 本地代码已经改好了，也已经用 Git 管理了，那以后怎么最快把更新发到线上？

### 9.1 先说推荐思路

当前项目最稳的发布方式不是在服务器上直接 `git pull` 编译，而是：

1. 在**本地**完成开发和测试
2. 本地打包前端和后端
3. 把产物上传到服务器覆盖

- 本地环境更熟悉，打包报错更好修
- 服务器不需要承担前端 Node 构建风险
- 不依赖服务器上完整源码环境
- 对当前这套宝塔部署方式最稳

## 9. 服务器重启后的恢复流程

这一节解决的问题是：

> 服务器重启之后，要检查哪些东西，怎样最快确认站点恢复正常。

### 9.1 先确认基础服务是否起来

服务器重启后，第一步不要先打开浏览器，而是先在服务器上确认系统服务。

#### 检查 Nginx

```bash
systemctl status nginx
```

如果你的系统没有 systemd 管理 nginx，也可以用：

```bash
nginx -t
ps -ef | grep nginx | grep -v grep
```

#### 检查后端服务

```bash
systemctl status erwang
```

如果状态不是 `active (running)`，先看日志：

```bash
journalctl -u erwang -n 100 --no-pager
```

#### 检查 MySQL

```bash
systemctl status mysqld
```

如果系统不是 `mysqld`，有时也可能是：

```bash
systemctl status mariadb
```

### 9.2 确认本机后端接口是否可用

只要后端起来了，就应该先测本机接口：

```bash
curl http://127.0.0.1:9090/api/articles
```

如果能返回 JSON，说明：

- Spring Boot 已启动成功
- 端口 9090 正常监听
- 数据库连接基本正常

### 9.3 确认 Nginx 反代是否正常

然后再测域名接口：

```bash
curl https://erwang.me/api/articles -k
```

如果这里通，但浏览器打不开页面，问题通常在前端静态文件或证书；
如果这里也不通，优先检查 Nginx 配置和证书。

### 9.4 浏览器恢复检查顺序

建议按这个顺序检查：

1. 打开 `https://erwang.me`
2. 看首页是否正常加载
3. 再试登录页、文章详情页、后台页
4. 再试刷新页面是否 404

### 9.5 如果重启后网站打不开，优先排查顺序

不要同时查很多地方，按下面顺序来：

1. `systemctl status erwang`
2. `journalctl -u erwang -n 100 --no-pager`
3. `curl http://127.0.0.1:9090/api/articles`
4. `nginx -t`
5. `curl https://erwang.me/api/articles -k`

这样可以快速判断问题是在：

- Java 没起来
- 数据库没起来
- Nginx 配置坏了
- HTTPS 证书不对

## 10. 本地 Git 代码改动后的快速发布流程

这一节解决的问题是：

> 以后本地代码改了，怎样最快把新版本上线，而不是重新从头部署一遍。

默认场景：

- 代码还是在本地 Git 仓库维护
- 服务器只是运行产物，不在服务器上开发

### 10.1 最快发布思路

今后的更新流程，不需要重新建站、重新建库，只需要按“变更类型”发布。

#### 情况 A：只改了前端

如果你只改了 Vue 页面、组件、样式，那么只需要：

1. 本地重新打包前端
2. 上传新的 `dist` 到服务器

命令：

```bash
cd /Users/miaozesheng/study/erwang/frontend
npm run build
scp -r /Users/miaozesheng/study/erwang/frontend/dist/* root@47.102.109.115:/www/wwwroot/erwang/
```

**作用：**

- 直接覆盖线上前端静态文件
- 不需要重启后端

#### 情况 B：只改了后端

如果你只改了 Java 代码、SQL 逻辑、接口行为，那么只需要：

1. 本地重新打包后端 jar
2. 上传新 jar
3. 重启后端服务

命令：

```bash
cd /Users/miaozesheng/study/erwang/backend
mvn clean package -DskipTests
scp /Users/miaozesheng/study/erwang/backend/target/blog-backend-1.0.0.jar root@47.102.109.115:/www/server/erwang/backend/app.jar
ssh root@47.102.109.115 "systemctl restart erwang && systemctl status erwang --no-pager"
```

**作用：**

- 替换线上 jar
- 让 systemd 重启新版本后端

#### 情况 C：前后端都改了

如果前后端都改了，就按顺序：

1. 打包前端
2. 打包后端
3. 上传前端
4. 上传后端
5. 重启后端

命令：

```bash
cd /Users/miaozesheng/study/erwang/frontend && npm run build
cd /Users/miaozesheng/study/erwang/backend && mvn clean package -DskipTests

scp -r /Users/miaozesheng/study/erwang/frontend/dist/* root@47.102.109.115:/www/wwwroot/erwang/
scp /Users/miaozesheng/study/erwang/backend/target/blog-backend-1.0.0.jar root@47.102.109.115:/www/server/erwang/backend/app.jar

ssh root@47.102.109.115 "systemctl restart erwang && systemctl status erwang --no-pager"
```

### 10.2 如果数据库结构变了怎么办

如果你后续修改了：

- 表结构
- 新增表
- 字段名
- 索引

那就不能只传 jar，必须额外处理 SQL。

推荐方式：

1. 在本地先写好变更 SQL
2. 在服务器数据库手动执行
3. 再上传新 jar

不要每次都直接 `DROP DATABASE`，那只适合“旧版本可完全覆盖”的首次部署阶段。

### 10.3 建议的日常发布原则

以后日常维护，建议遵守：

- **前端变更**：只发前端
- **后端变更**：只发 jar + 重启
- **数据库变更**：先备份，再执行 SQL
- **不要每次重建数据库**

## 12. 回滚与清理建议

### 12.1 最小回滚思路

如果一次更新后出了问题，回滚不要慌，按变更类型回滚。

#### 前端出问题

前提：你发布前最好留一份旧 `dist` 备份。

如果有备份，直接把旧前端静态文件重新覆盖回去。

#### 后端出问题

建议发布前先备份旧 jar：

```bash
cp /www/server/erwang/backend/app.jar /www/server/erwang/backend/app.jar.bak_$(date +%F_%H%M%S)
```

如果新版本出问题，可以把旧 jar 改回：

```bash
cp /www/server/erwang/backend/app.jar.bak_时间戳 /www/server/erwang/backend/app.jar
systemctl restart erwang
```

### 12.2 旧版本清理命令

这次部署完成后，旧版本后端和旧日志可以清理。

清理旧 Java 进程：

```bash
pkill -f "/www/wwwroot/blog-backend-1.0.0.jar"
```

删除旧 jar：

```bash
rm -f /www/wwwroot/blog-backend-1.0.0.jar
```

删除旧日志：

```bash
rm -f /www/wwwroot/app.log
rm -f /www/wwwroot/blog.log
```

确认旧端口已释放：

```bash
lsof -i :8081
```

如果没有输出，说明旧版本确实已经不在跑。

### 12.3 HTTPS 问题补充

如果以后再次出现“您的连接不是私密连接”，优先检查：

1. 宝塔 SSL 里绑定的证书是否包含 `erwang.me`
2. 是否包含 `www.erwang.me`
3. Nginx 使用的证书路径是不是旧域名证书

证书检查命令：

```bash
echo | openssl s_client -connect erwang.me:443 -servername erwang.me 2>/dev/null | openssl x509 -noout -subject -issuer -dates -ext subjectAltName
```

如果 SAN 不包含 `erwang.me` / `www.erwang.me`，就需要去宝塔重新签发证书。


查看后端最近日志：

```bash
journalctl -u erwang -n 100 --no-pager
```

查看后端进程：

```bash
ps -ef | grep app.jar | grep -v grep
```

检查 9090 是否监听：

```bash
lsof -i :9090
```

检查旧 8081 是否还残留：

```bash
lsof -i :8081
```

查看 MySQL 表：

```bash
mysql -uroot -p -D blog -e "SHOW TABLES;"
```

检查证书域名覆盖：

```bash
echo | openssl s_client -connect erwang.me:443 -servername erwang.me 2>/dev/null | openssl x509 -noout -subject -issuer -dates -ext subjectAltName
```
